문제 인식 · WHY

컨텍스트 윈도우는 무한하지 않다

긴 세션의 공통 증상 — 답변이 흐려지고, 한 시간 전 결정을 잊는다. 모델이 멍청해진 게 아니라 컨텍스트가 소음으로 가득 찼기 때문이다. 탐색 로그·테스트 출력처럼 한 번 읽고 버릴 내용이 대화를 점령한다.
지금까지 · 전부 메인에서
대화 하나에
탐색 + 로그 + 구현 전부
읽고 버릴 출력이 컨텍스트를 잠식 → 세션이 길어질수록 품질 하락. 새 세션을 열면 이번엔 맥락을 잃는다.

03
개념 정의 · WHAT

'서브에이전트'는 뭐가 다른가

특정 작업 전담으로 미리 구성해 둔 별도의 Claude 인스턴스. 필요할 때 메인 Claude가 일을 떼어 맡긴다.
1

독립된 컨텍스트 윈도우를 가진다

메인 대화 이력을 보지 못하는 대신, 메인 대화를 오염시키지도 않는다. 작업이 끝나면 결과 요약만 돌려준다.

2

자기만의 시스템 프롬프트로 움직인다

역할·작업 절차·출력 형식을 파일에 박아둔다. 매번 같은 지시를 반복할 필요가 없다.

3

도구·권한·모델을 따로 설정한다

읽기 전용 리뷰어, Bash만 쓰는 분석가처럼 필요한 도구만 허용. 값싼 모델로 돌려 비용도 아낀다.

4

파일이라서 재사용·공유가 된다

마크다운 파일 하나가 정의의 전부. git에 커밋하면 팀 전체가 같은 전문가를 쓴다.

핵심은 분리다 — 컨텍스트도, 프롬프트도, 권한도

당신은 시니어 코드 리뷰어입니다.

호출되면 git diff 로 변경부터 확인하고
수정된 파일에 집중해 즉시 리뷰합니다.

피드백은 Critical / Warning / Suggestion
우선순위로 정리해 제시합니다.
1

description

Claude가 "언제 이 에이전트를 부를지" 판단하는 유일한 근거. 구체적일수록 위임이 정확해진다.

2

tools

허용 도구 화이트리스트. Edit가 없으니 이 리뷰어는 읽기만 가능. 생략하면 메인의 도구 전부 상속.

3

본문 = 시스템 프롬프트

이 에이전트만의 헌법. 역할·절차·출력 형식을 여기 새긴다. Claude Code 기본 프롬프트는 받지 않는다.

바로 쓰는 공식 레시피 3종

🛡️

code-reviewer

tools: Read, Grep, Glob, Bash
model: inherit

읽기 전용 감시자. Edit가 없어 코드를 절대 건드리지 못한다.

  • git diff부터 확인하도록 절차 명시
  • Critical · Warning · Suggestion 3단 리포트
  • description에 "코드 수정 직후 능동적으로"
🔧

debugger

tools: Read, Edit, Bash, Grep, Glob
model: (생략 → inherit)

고치는 것까지가 일. 그래서 리뷰어와 달리 Edit를 준다.

  • 에러 캡처 → 재현 → 원인 격리 → 최소 수정 → 검증
  • "증상이 아니라 근본 원인을 고쳐라" 명시
📊

data-scientist

tools: Bash, Read, Write
model: sonnet

코딩 밖 업무도 된다. SQL·BigQuery 분석 전담 요원.

  • 쿼리 접근법 · 가정 · 핵심 발견을 함께 보고
  • "비용 효율적인 쿼리"를 프롬프트로 강제

활용 패턴 · PATTERNS

성능을 뽑아내는 패턴 3가지

1

대용량 출력 격리

"테스트 스위트 전체 돌리고, 실패한 것만 에러 메시지와 함께 보고해줘" — 테스트 · 로그 · 문서 수집처럼 장황한 출력은 밖에서 소화시킨다.

2

병렬 리서치

"인증 · DB · API 모듈을 각각 서브에이전트로 동시에 조사해줘" — 서로 의존이 없는 조사에 최적. 각자 끝나면 메인 Claude가 종합한다.

3

체이닝 (파이프라인)

"code-reviewer로 성능 문제 찾고 → optimizer로 수정해줘" — 앞 에이전트의 결과를 다음 에이전트에 넘기는 단계별 워크플로.

단, 여러 에이전트가 상세 결과를 잔뜩 돌려주면 그것도 컨텍스트 소모다. "핵심만 요약해 보고"를 습관처럼 붙이자.
무거운 작업은 밖에서, 결론만 안으로

판단 기준 · WHEN NOT

쓰지 말아야 할 때도 있다

🧭

이럴 땐 그냥 메인에서

  • 왕복 피드백이 잦은 작업 — 위임하면 오히려 느려진다
  • 계획 → 구현 → 테스트가 같은 맥락을 공유할 때 — 쪼개면 맥락이 끊긴다
  • 빠른 단건 수정 — 서브에이전트는 매번 컨텍스트를 새로 모은다 (지연 비용)
⚠️

위임할 때 기억할 것

  • 호출마다 새 인스턴스 = 이전 기억 없음 — 이어가려면 "아까 그 리뷰 이어서" (재개 가능)
  • 돌려받는 리포트도 컨텍스트 비용 — 요약 형식을 프롬프트에 못 박기
  • 도구는 최소만 — 안전과 집중, 둘 다를 위해
메인 컨텍스트에서 돌릴 재사용 워크플로라면 Skills가, 대화 중 곁다리 질문 하나라면 /btw가 더 낫다. 도구는 목적에 맞게.
위임이 항상 정답은 아니다

14
고급 기능 · ADVANCED 2026

서브에이전트는 계속 진화 중

🪆

중첩 위임

서브에이전트가 또 서브에이전트를 부른다 (최대 깊이 5). 리뷰어가 발견 건마다 검증 에이전트를 파견하는 식 — 중간 산출물은 내 대화에 오지 않는다.

🔁

이어서 작업 (Resume)

끝난 에이전트를 대화 이력째 재개할 수 있다. "그 리뷰 이어서, 이번엔 인가 로직 봐줘" 한마디면 이전 맥락 그대로 계속.

🧠

영속 메모리

memory: project를 주면 배운 패턴이 세션이 끝나도 쌓인다. 쓸수록 우리 코드베이스에 밝아지는 팀원.
