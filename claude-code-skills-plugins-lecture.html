03
개념 정의 · WHAT

스킬은 폴더 하나가 전부다

1

SKILL.md 하나면 성립한다

폴더 이름이 곧 명령어가 된다. .claude/skills/deploy/SKILL.md 를 만들면 그 순간 /deploy 가 생긴다.

2

내가 부르거나 Claude가 알아서 부른다

/이름 으로 직접 부를 수도 있고, description을 보고 Claude가 판단해 자동으로 꺼내 쓸 수도 있다.

3

파일을 곁들일 수 있다

템플릿, 예시, 참고 문서, 실행 스크립트를 같은 폴더에 둔다. 필요할 때만 읽히므로 컨텍스트가 새지 않는다.

4

표준을 따르는 개방 포맷이다

Agent Skills 개방 표준을 따라 다른 AI 도구에서도 통한다. Claude Code는 여기에 호출 제어·서브에이전트 실행 등을 얹었다.

중요한 변화 — 커스텀 명령(.claude/commands/)은 스킬로 통합됐다. 기존 파일은 그대로 동작하지만, 새로 만든다면 스킬 쪽이 폴더·프론트매터·자동 호출을 쓸 수 있어 유리하다.
폴더를 만드는 순간 명령어가 생긴다

04
핵심 원리 · PROGRESSIVE DISCLOSURE

스킬이 가벼운 이유 — 3층으로 나눠 연다

1층

메타데이터 — name · description

항상 로딩된다. Claude는 이 한 줄만 보고 "이 스킬을 꺼낼지" 판단한다. 그래서 description이 스킬의 성패를 가른다.

상시 · 아주 작음
2층

SKILL.md 본문 — 실제 지시문

호출될 때만 로딩된다. 절차·규칙·예시가 여기 들어간다. 단, 한 번 열리면 세션 내내 남는다(9번 슬라이드).

호출 시 · 중간
3층

참고 파일 · 스크립트 — reference.md scripts/

실제로 필요할 때만. 스크립트는 아예 실행만 되고 내용은 안 읽힌다 — 출력만 토큰을 쓴다. 여기가 용량을 마음껏 써도 되는 곳이다.

필요 시 · 얼마든지
이 구조 덕분에 스킬을 많이 만들어도 부담이 적다 — 안 쓰는 스킬은 설명 한 줄만 자리를 차지한다. 반대로 SKILL.md 본문에 참고 자료를 몰아넣으면 이 장점이 사라진다. 공식 권장은 본문 500줄 이내.
무거운 건 3층으로 내려보내라

Claude가 부르면 곤란한 것

disable-model-invocation: true

부작용이 있는 작업. 커밋·배포·메시지 발송처럼 시점을 내가 정해야 하는 일. 코드가 그럴듯해 보인다고 Claude가 배포를 결정하면 곤란하다.

  • 덤으로 컨텍스트도 아낀다 — 설명조차 안 올라간다
📖

내가 부를 일이 없는 것

user-invocable: false

배경지식. "이 레거시 시스템은 이렇게 동작한다" 같은 내용은 Claude가 알아야 하지만, 내가 /legacy-context를 칠 일은 없다.

놓치기 쉬운 것 · LIFECYCLE

한 번 열린 스킬은 세션 내내 남는다

스킬을 호출하면 그 내용이 대화에 메시지 하나로 들어와 끝까지 머문다. Claude는 이후 턴에서 파일을 다시 읽지 않는다. 여기서 두 가지가 따라온다.
💰

본문의 모든 줄이 반복 비용

한 번 로딩되면 매 턴 다시 읽힌다. 그래서 "왜 이렇게 하는지"를 길게 설명하지 말고 "무엇을 하라"만 적는 게 좋다. CLAUDE.md에 적용하는 간결함 기준을 그대로 쓰면 된다.

📌

일회성 단계가 아니라 상시 지침으로

작업 내내 지켜야 할 내용이라면 "먼저 ~하라"가 아니라 "항상 ~한다"로 쓴다. 다시 읽히지 않으므로 한 번 쓴 문장이 계속 작동해야 한다.

압축될 때는? 자동 압축이 일어나면 호출했던 스킬들을 요약 뒤에 다시 붙여준다 — 스킬당 앞부분 5,000토큰까지, 전체 합계 25,000토큰 한도. 최근 것부터 채우므로 한 세션에서 스킬을 많이 부르면 오래된 것은 통째로 빠진다. 그래서 중요한 지시는 SKILL.md 맨 앞에 두는 게 안전하다.
스킬 본문은 짧을수록 오래 산다

점검·리뷰

/doctor · /code-review · /debug

/doctor는 설치 상태와 스킬 목록의 컨텍스트 비용까지 알려준다. /code-review는 내가 부를 때만 돈다.

▶️

실행·검증

/run · /verify · /run-skill-generator

테스트가 아니라 앱을 실제로 띄워서 변경을 확인한다. 실행 절차가 복잡한 프로젝트라면 /run-skill-generator로 레시피를 기록해 두자.

🔁

반복·일괄

/batch · /loop · /claude-api

같은 작업을 여러 대상에 돌리거나 주기적으로 실행한다. 전부 끄려면 설정에 disableBundledSkills.

플러그인 해부 · STRUCTURE

플러그인은 정해진 폴더 이름이 전부다

my-plugin/ ├── .claude-plugin/ │ └── plugin.json ← 이름·버전 (여기엔 이것만!) ├── skills/ ← 스킬 │ └── code-review/SKILL.md ├── agents/ ← 서브에이전트 ├── hooks/hooks.json ← 훅 ├── .mcp.json ← MCP 서버 ├── .lsp.json ← 코드 인텔리전스 ├── monitors/ ← 백그라운드 감시 └── bin/ ← 실행 파일 (PATH에 추가)
⚠️

가장 흔한 실수

skills/ agents/ hooks/ 를 .claude-plugin/ 안에 넣으면 안 된다. 그 폴더에는 plugin.json만 들어간다. 나머지는 전부 플러그인 루트에.

.claude-plugin/plugin.jsonMANIFEST
{
  "name": "my-plugin",   ← 네임스페이스
  "description": "...",
  "version": "1.0.0"
}
이름이 곧 네임스페이스다 — my-plugin의 hello 스킬은 /my-plugin:hello가 된다. 덕분에 두 플러그인이 똑같이 deploy를 가져도 충돌하지 않는다. version을 적지 않으면 커밋마다 새 버전으로 취급된다.
폴더 이름만 맞추면 알아서 인식된다

설치는 코드 실행과 같다

🔐

내 권한으로 돌아간다

공식 문서의 경고 그대로 — 플러그인과 마켓플레이스는 내 사용자 권한으로 임의의 코드를 실행할 수 있다. Anthropic은 서드파티 내용물을 검증하지 않는다. 믿는 출처만.

📥

남의 스킬도 읽어보고

스킬은 allowed-tools로 스스로에게 도구 권한을 줄 수 있고, 셸 명령도 심을 수 있다. 저장소를 신뢰하기 전에 프로젝트 스킬을 훑어보자.

🗑️

마켓 제거 = 플러그인 제거

마켓플레이스를 지우면 거기서 설치한 플러그인이 전부 사라진다. 정리하기 전에 무엇이 딸려 나가는지 확인하자.

📉

설명이 잘려나간다

스킬이 많으면 목록 예산을 넘겨 덜 쓰는 스킬부터 설명이 삭제된다. /doctor로 비용을 확인하자.

🧹

안 쓰는 건 정리

/plugin Installed 탭이 오래 안 쓴 플러그인을 따로 모아 보여준다. 고정비만 내고 있는 것들이다.

🎯

안 튀어나오면 description

스킬이 안 불리면 내가 쓸 법한 단어가 설명에 있는지 보자. 반대로 너무 자주 나오면 더 구체적으로.
