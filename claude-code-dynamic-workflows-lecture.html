문제 인식 · WHY

모델이 지휘하면 매번 다른 공연이 된다

에이전트를 여러 개 띄우는 것 자체는 이미 할 수 있다. 문제는 몇 명을 띄울지, 무엇을 먼저 할지, 언제 멈출지를 모델의 그때그때 판단에 맡긴다는 점이다. 재현되지 않는 오케스트레이션은 검증할 수도, 재개할 수도 없다.

정의 · WHAT

워크플로우는 에이전트를 부리는 스크립트다

가장 작은 완성된 워크플로우JS
export const meta = {
  name: 'find-flaky-tests',
  description: '깨지는 테스트를 찾아 고친다',
  phases: [
    { title: 'Scan', detail: 'CI 로그에서 재시도 흔적' },
    { title: 'Fix',  detail: '테스트 하나당 에이전트 하나' },
  ],
}

phase('Scan')
const flaky = await agent('CI 로그에서 retry 마커를 찾아라',
                          { schema: FLAKY_SCHEMA })

phase('Fix')
const fixes = await pipeline(flaky.tests,
  t => agent(`${t.name} 의 불안정 원인을 고쳐라`))

return { fixes }
🌙

백그라운드로 돈다

호출하면 즉시 태스크 ID를 돌려주고 뒤에서 실행된다. 끝나면 알림이 오고, 진행 상황은 /workflows로 실시간으로 본다.

💾

스크립트는 자동으로 남는다

모든 실행은 스크립트를 세션 디렉터리에 저장하고 경로를 결과에 실어 준다. 고쳐서 scriptPath로 다시 돌리면 된다.

📄

파일로 먼저 쓰지 않는다

최초 실행은 script에 인라인으로 넘긴다. Write로 파일을 만든 뒤 실행하는 순서가 아니다.

대본을 쓰고, 배우를 부른다

04
쓰는 이유 · MOTIVES

세 가지 중 하나에 걸릴 때만 값어치를 한다

🕸️

포괄성

Comprehensive

일을 쪼개서 병렬로 덮는다. 혼자 순차로 훑으면 뒤로 갈수록 앞을 잊는다. 감사·전수 조사·다각도 리서치가 여기 속한다.

⚖️

확신

Confident

결론을 내리기 전에 독립적 관점과 적대적 검증을 통과시킨다. 그럴듯하지만 틀린 발견을 걸러 내는 것이 목적이다.

🏗️

규모

Scale

한 컨텍스트 창에 애초에 들어가지 않는 일. 대규모 마이그레이션, 저장소 전체 스윕, 수백 개 파일 변환이 대표적이다.

반대로 — 파일 하나를 고치는 일, 이미 답을 아는 질문, 대화형 응답에는 쓰지 않는다. 에이전트 스폰 비용이 작업 자체보다 비싸진다.
✅

어울리는 일

"이 저장소를 철저히 감사해줘" · "이 API를 전 파일에서 새 시그니처로 옮겨줘" · "설계안 셋을 만들어 비교해줘"

🚫

어울리지 않는 일

"이 오타 고쳐줘" · "이 함수 뭐 하는 거야" · "테스트 한 번 돌려줘" — 혼자 하는 편이 빠르고 싸다.

문법 ② · API 지도

스크립트가 쓸 수 있는 훅은 여덟 개뿐이다

agent(prompt, opts?) → Promise<any>

서브에이전트 하나를 띄운다. schema가 없으면 최종 텍스트(문자열), 있으면 검증된 객체를 돌려준다.

pipeline(items, stage1, stage2, …) → Promise<any[]>

각 아이템을 서로 기다리지 않고 모든 스테이지에 통과시킨다. 다중 스테이지 작업의 기본값이다.

parallel(thunks) → Promise<any[]>

동시에 돌리고 전부 끝날 때까지 기다린다 — 대기선(배리어)이다. 실패한 항목은 null이 되며 호출 자체는 실패하지 않는다.

phase(title) · log(message)

진행 그룹을 나누고, 사용자에게 한 줄 진행 메시지를 띄운다.

args · budget

호출 시 넘긴 입력값과, 이번 턴의 토큰 예산 정보.

workflow(nameOrRef, args?) → Promise<any>

다른 워크플로우를 하위 단계로 실행한다. 중첩은 한 단계까지 — 자식 안에서 또 부르면 예외가 난다.

훅은 적고, 조합은 무한하다

문법 ③ · agent 옵션

agent()의 옵션 일곱 가지

label
진행 화면에 뜨는 이름을 바꾼다. review:auth.ts처럼 무엇을 보고 있는지가 드러나게 쓴다.
phase
이 에이전트를 특정 진행 그룹에 명시적으로 넣는다. pipeline·parallel 안에서는 전역 phase()가 경합하므로 반드시 이 옵션을 쓴다.
schema
JSON 스키마를 주면 에이전트가 구조화 출력 도구를 강제로 호출하고, 검증된 객체가 반환된다.
model
모델을 바꾼다. 기본은 생략 — 생략하면 세션 모델을 물려받고, 그게 거의 항상 옳다.
effort
추론 강도. low는 기계적인 단계에, xhigh·max는 가장 어려운 검증·심판 단계에만 쓴다.
isolation
'worktree'면 전용 git 워크트리에서 돈다. 비싸다 — 병렬로 파일을 고쳐 충돌이 날 때만.
agentType
커스텀 서브에이전트 타입을 지정한다. schema와 함께 쓸 수 있다.
반드시 기억할 것 — 사용자가 중간에 건너뛰거나 API 오류로 죽으면 agent()는 null을 돌려준다. 결과를 쓰기 전에 .filter(Boolean)을 습관처럼 붙인다.
기본값을 믿고, 필요할 때만 덮어쓴다

문법 ④ · SCHEMA

파싱하지 말고 스키마를 건네자

스키마 없이 — 문자열이 온다FRAGILE
const txt = await agent('버그를 JSON으로 내놔')
const bugs = JSON.parse(txt)  // 💥 설명이 섞이면 터진다
스키마를 주면 — 검증된 객체가 온다SAFE
const BUGS = {
  type: 'object',
  properties: {
    bugs: { type: 'array', items: { type: 'object',
      properties: {
        file:     { type: 'string' },
        line:     { type: 'number' },
        severity: { enum: ['high','med','low'] },
      }, required: ['file','severity'] } },
  }, required: ['bugs'],
}

const r = await agent('버그를 찾아라', { schema: BUGS })
r.bugs.filter(b => b.severity === 'high')  // 바로 쓴다
🔒

검증이 도구 층에서 일어난다

스키마를 주면 에이전트는 구조화 출력 도구를 반드시 호출해야 한다. 형식이 안 맞으면 모델이 그 자리에서 다시 시도한다 — 내 스크립트까지 깨진 값이 흘러오지 않는다.

🤖

에이전트는 사람에게 말하지 않는다

서브에이전트에게는 "네 최종 텍스트가 곧 반환값이다"라고 미리 알려져 있다. 그래서 인사말이나 요약 없이 날것의 데이터를 돌려준다.

⚠️

필수 필드를 아끼지 말자

required가 비면 모델은 편한 필드만 채운다. 뒤 단계에서 반드시 읽을 값은 전부 required에 넣는다.

판별법 · WHEN TO BARRIER

배리어는 딱 세 경우에만 정당하다

정당하다 · N단계가 N-1단계 전체를 봐야 할 때
✓
전체 결과를 합쳐 중복을 제거해야 그다음 비싼 작업이 헛돌지 않을 때
✓
총합이 0이면 조기 종료할 때 — "버그가 0건이면 검증 단계를 통째로 건너뛴다"
✓
다음 단계 프롬프트가 "다른 발견들"을 비교 대상으로 참조할 때
정당한 배리어OK
const all = await parallel(DIMS.map(d => () =>
  agent(d.prompt, { schema: FINDINGS })))
// ↓ 전부 모여야만 가능한 일
const deduped = dedupe(all.filter(Boolean).flatMap(r => r.findings))
정당하지 않다 · 흔한 착각 셋
✕
"먼저 flatten/map/filter 해야 해서" — 그건 파이프라인 스테이지 안에서 하면 된다
✕
"개념적으로 분리된 단계라서" — 파이프라인이 모델링하는 게 바로 그거다. 단계가 나뉜 것 ≠ 동기화
✕
"코드가 더 깔끔해서" — 배리어의 지연은 실재하는 비용이다
변환은 스테이지 안으로FIX
pipeline(items,
  stageA,
  r => transform([r]).flat(),   // 배리어 없이 처리
  stageB)
헷갈리면 파이프라인이다. 배리어는 "정말 전부 한자리에 있어야 하는가"라는 질문에 구체적인 이유를 댈 수 있을 때만 쓴다.

냄새 맡기 · SMELL TEST

이 세 줄이 보이면 거의 항상 잘못됐다

냄새나는 코드SMELL
const a = await parallel(…)
const b = transform(a)   // flatten · map · filter
                        // 아이템 간 의존이 전혀 없다
const c = await parallel(b.map(…))
고친 코드FIXED
const c = await pipeline(items,
  item => agent(…),      // 1단계
  r    => transform(r),   // 변환도 스테이지다
  t    => agent(…))       // 2단계
🔁

스테이지 인자를 쓰자

모든 스테이지 콜백은 (prevResult, originalItem, index)를 받는다. 뒷 단계에서 원본 아이템으로 라벨을 만들 수 있으니, 1단계 반환값에 컨텍스트를 끼워 넣지 않아도 된다.

💥

실패는 격리된다

스테이지가 예외를 던지면 그 아이템만 null이 되고 남은 스테이지를 건너뛴다. 다른 아이템은 계속 흐른다.

🕳️

parallel도 안 터진다

thunk가 던져도 그 자리에 null이 들어갈 뿐 호출 자체는 reject하지 않는다. 그래서 결과를 쓰기 전 .filter(Boolean)은 선택이 아니다.

중간의 transform은 배리어를 정당화하지 못한다

종합 · COMPOSITION

패턴 넷을 한 스크립트에 겹쳐 본다

전수 리뷰 · 찾기 → 중복 제거 → 다중 렌즈 → 마를 때까지FULL
const seen = new Set(), confirmed = []
let dry = 0

while (dry < 2) {                         // ④ 마를 때까지
  const found = (await parallel(FINDERS.map(f => () =>
    agent(f.prompt, { phase: 'Find', schema: BUGS }))))
    .filter(Boolean).flatMap(r => r.bugs)

  const fresh = found.filter(b => !seen.has(key(b)))  // ② 중복 제거
  if (!fresh.length) { dry++; continue }
  dry = 0; fresh.forEach(b => seen.add(key(b)))

  const judged = await parallel(fresh.map(b => () =>  // ③ 다중 렌즈
    parallel(['correctness','security','repro'].map(lens => () =>
      agent(`"${b.desc}" 를 ${lens} 렌즈로 판정하라`,
            { phase: 'Verify', schema: VERDICT })))
      .then(vs => ({ b,
        real: vs.filter(Boolean).filter(v => v.real).length >= 2 }))))

  confirmed.push(...judged.filter(v => v.real).map(v => v.b))
}
return confirmed
🔑

중복 제거는 seen 기준이다

confirmed 기준으로 걸러 내면 심판이 기각한 발견이 매 라운드 되살아나 루프가 영원히 끝나지 않는다. 본 것 전부를 seen에 넣어야 수렴한다.

🧮

중복 제거는 에이전트가 아니라 코드다

키가 같은지 비교하는 일에 모델을 쓰지 않는다. 결정론으로 되는 일은 결정론으로.

🚪

여기의 배리어는 정당하다

라운드 안의 parallel은 이번 라운드 결과 전체를 seen과 대조해야 하므로 진짜로 모여야 한다.

에이전트마다 새 git 워크트리가 붙는다. 각자 저장소의 독립 사본에서 작업하므로 충돌이 원천적으로 없다. 변경이 없으면 자동으로 정리된다.

💰

공짜가 아니다

에이전트마다 200~500ms의 셋업 시간과 디스크 공간이 든다. 20개를 띄우면 그 비용이 그대로 스무 배다.

✅

이럴 때만 켠다

대규모 이전 · 파일 단위 리팩터링 · 여러 시안을 실제로 구현해 비교할 때. 한마디로 병렬로 쓰기(write)를 할 때다.

🚫

읽기만 하면 필요 없다

리뷰·리서치·탐색처럼 파일을 읽기만 하는 팬아웃에 워크트리를 붙이는 건 순수한 낭비다.

상시 동의 모드 — 기본이 워크플로우가 된다

켜져 있을 때

ON

모든 실질적 작업에 기본으로 워크플로우를 짜서 실행한다. 목표는 가능한 한 가장 철저하고 정확한 결과이며, 토큰 비용은 제약이 아니다. 다단계 작업이라면 이해 → 설계 → 구현 → 리뷰를 단계마다 한 판씩 이어 돌린다.

그래도 혼자 하는 경우

SOLO

대화만 오가는 턴, 그리고 기계적인 사소한 편집. 이미 검증이 끝난 일도 마찬가지다.

🔀

단발 키워드로도 켠다

프롬프트에 ultracode를 한 번 넣으면 그 턴에만 열린다. 세션 전체로 켜면 상시 동의가 된다.

🎚️

규모는 요청에 맞춘다

"버그 있나 봐줘"는 파인더 서넛에 단일 검증. "철저히 감사해줘"는 파인더 풀을 키우고 3~5표 적대적 검증에 종합 단계까지. 감사·리뷰·리서치는 철저히, 빠른 확인은 짧게.

↩️

꺼지면 원래대로

점검표 · ANTI-PATTERNS

돌리기 전에 여덟 줄만 확인하자

1
변환 하나 때문에 배리어를 넣지 않았나 — 스테이지 안으로 옮긴다
2
.filter(Boolean)을 빼먹지 않았나 — 스킵·오류는 null로 온다
3
pipeline 안에서 전역 phase()에 기대지 않았나 — opts.phase로 명시한다
4
중복 제거를 확정 목록 기준으로 하지 않았나 — 루프가 수렴하지 않는다
5
budget.total 가드 없이 while을 돌리지 않았나 — Infinity로 폭주한다
6
필요 없는데 isolation: 'worktree'를 켜지 않았나 — 읽기 전용이면 낭비다
7
잘라낸 범위를 log()로 알리지 않았나 — 조용한 절삭은 거짓말이 된다
8
확신도 없이 model을 덮어쓰지 않았나 — 모르면 생략이 정답이다
